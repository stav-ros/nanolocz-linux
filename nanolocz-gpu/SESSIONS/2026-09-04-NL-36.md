## Technical Decisions

### 1. Library Selection for HMM
- **Chosen:** `hmmlearn` — Mature, scikit-learn compatible API
- **Rationale:** Well-maintained, familiar interface, supports Gaussian HMMs with full covariance
- **Alternative considered:** `pomegranate` (more modern but less stable API)

### 2. Change-Point Detection Algorithm
- **Default:** PELT (Pruned Exact Linear Time) — Optimal for most cases
- **Alternatives provided:** Binary segmentation (faster but approximate), Window-based
- **Library:** `ruptures` — Comprehensive implementation with multiple cost functions

### 3. Gap Handling in Traces
- **Strategy:** Linear interpolation for small gaps (< max_gap_size frames)
- **Large gaps:** Remain as NaN, excluded from HMM fitting
- **Rationale:** Preserves data integrity while allowing minor gap filling

### 4. Model Selection
- **Criteria:** BIC (Bayesian Information Criterion) by default, AIC available
- **Range:** Tests 2 to max_states (default 10)
- **Selection:** Minimum BIC/AIC score determines optimal n_states

## Known Limitations

1. **GPU Acceleration Not Implemented**
   - Current HMM fitting is CPU-only via hmmlearn
   - Future work: Custom CuPy implementation or RAPIDS integration

2. **Missing Data Handling**
   - Large gaps (>max_gap_size) are excluded from analysis
   - Future: HMM variants that explicitly model missing observations

3. **Single-Feature HMM**
   - Currently fits HMM to one feature at a time
   - Future: Multi-variate HMM using multiple features simultaneously

4. **No Batch Processing Optimization**
   - Processes all traces sequentially
   - Future: Parallel processing for large datasets
